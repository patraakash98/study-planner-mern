# Study Planner — MERN Architecture and Coding-Agent Prompt

## 1. Goal and scope

Build a beginner-friendly web application to add study tasks, record their course and topic, assign priority and estimated duration, mark them completed, and view pending or completed tasks.

MERN means MongoDB (database), Express (HTTP API framework), React (browser interface), and Node.js (server runtime).

First version: a single-user application running locally, with persistent MongoDB storage. Login, multiple users, due dates, calendars, reminders, timers, editing, and deletion are future features. This version has no user isolation and must not be exposed as a public personal planner without adding authentication and authorization.

## 2. Features

| Feature | Behaviour |
| --- | --- |
| Add task | Form with task name, course name, topic name, priority, and duration |
| Priority | Select High, Medium, or Low; default Medium |
| Duration | Estimated study time in positive whole minutes |
| Initial status | Every new task starts as Pending |
| Complete task | A button marks a pending task Completed |
| View tasks | All, Pending, and Completed tabs; Pending selected initially |
| Persistence | Tasks remain after refreshing or restarting the application |
| Feedback | Loading indicators, validation messages, empty states, and retryable errors |

Course and topic are text fields in this version. Adding a course or topic means entering its name on a task; separate course/topic management is unnecessary for the initial requirements.

## 3. Simple architecture

| Layer | Technology | Responsibility |
| --- | --- | --- |
| Browser | React with Vite, JavaScript, plain CSS | Show form and task list; call API; show results |
| API | Node.js and Express, JavaScript ES modules | Validate requests, perform task operations, return JSON |
| Data access | Mongoose | Define task schema and communicate with MongoDB |
| Database | MongoDB | Persist task documents in a tasks collection |

Use one repository containing a client directory and a server directory. The browser only calls Express; it never connects directly to MongoDB. Keep database credentials on the server.

Backend responsibilities: routes map URLs to controllers; controllers validate input and perform operations; the Task model defines stored data; error middleware produces consistent errors. A separate service/repository layer is not needed for three endpoints.

Frontend responsibilities: App owns task/filter/loading/error state; small components render the form, tabs, list, and task cards. Use React hooks and native fetch. Redux and a routing library are unnecessary for this single page.

## 4. Data structure

Store one MongoDB document per task. In React, represent tasks as an array of objects, using each MongoDB `_id` as the list key.

| Field | Type | Rules |
| --- | --- | --- |
| `_id` | MongoDB ObjectId | Generated by MongoDB; exposed as a string in JSON |
| `taskName` | String | Required, trimmed, 1–150 characters |
| `courseName` | String | Required, trimmed, 1–100 characters |
| `topicName` | String | Required, trimmed, 1–150 characters |
| `priority` | String enum | `high`, `medium`, or `low`; default `medium` |
| `durationMinutes` | Number | Required integer, 1–1440 inclusive |
| `status` | String enum | `pending` or `completed`; default `pending` |
| `createdAt` | Date | Automatically recorded by Mongoose timestamps |
| `updatedAt` | Date | Automatically updated by Mongoose timestamps |

The 1440-minute limit is an explicit MVP design choice to catch accidental input; it can be changed later. Duration is an estimate, not a countdown or time spent.

Example API task object:

```json
{
  "_id": "507f1f77bcf86cd799439011",
  "taskName": "Solve five practice questions",
  "courseName": "Python",
  "topicName": "NumPy indexing",
  "priority": "high",
  "durationMinutes": 30,
  "status": "pending",
  "createdAt": "2026-09-27T11:00:00.000Z",
  "updatedAt": "2026-09-27T11:00:00.000Z"
}
```

Do not store both `completed` and `status`: they could contradict each other. Duplicate names are allowed because distinct tasks have distinct IDs. Store course and topic names inside each task to avoid extra collections and relationships initially.

## 5. REST API contract

| Method | Endpoint | Behaviour | Success |
| --- | --- | --- | --- |
| GET | `/api/tasks` | Return all tasks, newest first | 200 |
| GET | `/api/tasks?status=pending` | Return pending tasks, newest first | 200 |
| GET | `/api/tasks?status=completed` | Return completed tasks, newest first | 200 |
| POST | `/api/tasks` | Create a pending task | 201 |
| PATCH | `/api/tasks/:id/status` | Set status to completed | 200 |

For the All tab, omit the status query parameter. Reject unsupported status values with 400. Break equal creation-time ties using `_id` descending for consistent ordering.

POST request:

```json
{
  "taskName": "Solve five practice questions",
  "courseName": "Python",
  "topicName": "NumPy indexing",
  "priority": "high",
  "durationMinutes": 30
}
```

The frontend converts the duration input to a number before sending it. The server independently checks types and limits. Allow only these five POST properties; reject unknown fields, including client-supplied status or IDs.

PATCH request:

```json
{ "status": "completed" }
```

Allow only the status property and only the value `completed` in this MVP. Repeating completion succeeds and returns the already completed task; it must not create another record. Reopening tasks is outside the initial scope.

Successful list response: `{ "tasks": [] }` or an array of task objects inside `tasks`. Successful create/update response: `{ "task": { ... } }`.

Error response example:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Please correct the highlighted fields.",
    "fields": { "durationMinutes": "Enter a whole number from 1 to 1440." }
  }
}
```

Use 400 for invalid JSON, invalid fields, invalid query values, or malformed ObjectIds; 404 for a well-formed task ID that does not exist; 503 for database unavailability; and 500 for unexpected errors. Do not expose stack traces or credentials to the browser. Return an empty list with 200 when nothing matches.

## 6. User interface and request flow

Use one responsive page with a Study Planner heading, an Add Task form, status tabs, and task cards. Each card displays task name, course, topic, priority, duration, status, and a Mark Completed button only when pending. Priority badges must include text, not only colours.

### Adding a task

1. User fills the form and selects Add Task.
2. React validates fields and disables submission while the request is pending.
3. Express validates the JSON and Mongoose writes the task to MongoDB.
4. The API returns the saved task with its ID.
5. React resets the form, selects Pending, and refreshes that list from the API.
6. On failure, keep form values and display a useful error.

### Completing a task

1. Disable that task's button during its PATCH request.
2. Only show success after the server confirms the update.
3. Refresh the active filter. A completed task disappears from Pending and appears under Completed and All.
4. On failure, preserve the existing task and allow retry.

Abort or ignore obsolete list requests so rapidly switching tabs cannot display results belonging to an older filter. Distinguish a failed mutation from a successful mutation followed by a failed list refresh; do not invite users to submit an already-saved task again.

## 7. Edge cases

| Case | Handling |
| --- | --- |
| Whitespace-only names | Trim and reject |
| Names beyond maximum length | Field-specific validation error |
| Invalid priority | Reject server-side; select control prevents normal UI mistakes |
| Empty, text, decimal, negative, zero, or excessive duration | Require numeric integer within range |
| Duplicate task names | Allow; use IDs for updates |
| No tasks or no matching tasks | Friendly filter-specific empty message |
| Double-click submission | Disable Add while saving; do not automatically retry POST |
| Completion repeated | Return existing completed task successfully |
| Invalid or missing ID | Distinguish 400 from 404 |
| API offline | Show error and retry control without crashing |
| Database unavailable | Fail startup clearly or return safe 503 after connection loss |
| Tab changes during a request | Ignore/abort stale responses |
| Refresh or server restart | Reload persisted tasks from MongoDB |
| Unexpected request properties | Reject instead of passing arbitrary request objects to MongoDB |
| HTML entered as task text | Render as plain React text; do not use raw HTML injection |

Disabling the submit button prevents ordinary double-clicks, but does not guarantee exactly-once creation after ambiguous network failures. Avoid automatic POST retries in the MVP.

## 8. Configuration and running locally

Use JavaScript throughout and a supported Node.js LTS release compatible with selected dependencies. Select compatible package versions during implementation and commit lockfiles. No exact versions are prescribed by this architecture.

Example backend configuration:

```dotenv
PORT=5000
HOST=127.0.0.1
MONGODB_URI=mongodb://127.0.0.1:27017/study_planner
```

The local MongoDB address assumes MongoDB is installed and running. Alternatively, the user can provide a MongoDB Atlas connection string in the server environment. Never commit real credentials or put the MongoDB URI in React configuration.

The coding agent should configure Vite to proxy `/api` requests to `http://127.0.0.1:5000`; frontend code calls relative `/api/...` paths. This avoids needing cross-origin configuration during local development. Bind development services to loopback for this unauthenticated MVP.

README must explain prerequisites, installation in both directories, copying `.env.example` to `.env`, starting MongoDB, and running frontend and backend in two terminals. Include Windows-friendly instructions, actual working script names, and troubleshooting for missing database connections or ports already in use.

## 9. Implementation milestones

1. Scaffold client/server, scripts, environment template, and README.
2. Implement MongoDB connection, Task schema, and the three API operations.
3. Implement React form, cards, filters, and API calls.
4. Add validation, accessible feedback, responsive CSS, and request-state handling.
5. Verify persistence and key error paths; complete setup documentation.

## 10. Acceptance criteria

- A valid task is stored in MongoDB and visible in Pending after creation.
- Every requested task detail appears in the interface.
- Completing a task changes its stored status and updates the selected list.
- Pending and Completed filters return the correct records; All returns both.
- Reloading the browser and restarting the server preserve records.
- Invalid inputs cannot create or corrupt records, including requests made directly to the API.
- Empty lists, API failures, and in-flight actions have clear UI states.
- The interface works on a narrow mobile viewport and with keyboard controls and labelled inputs.
- Frontend production build succeeds, and the documented startup steps match the project.
- API tests cover creation/default status, validation, status filters, completion and repeated completion, malformed IDs, and missing IDs. Tests use an isolated test database and never erase development data.
- Any verification blocked by unavailable dependencies or MongoDB is reported honestly with exact steps for the user to run.
